# Требования к внешним интеграциям PropDevelopment

## Функциональные требования (FR)

| ID | Требование |
|---|---|
| FR-1 | Внешняя интеграция должна обеспечивать работу сервисов **«Интеллектуальный домофон»** и **«Интеллектуальный шлагбаум»** через текущее мобильное приложение для собственников. |
| FR-2 | Система должна позволять собственнику удалённо выполнять команды управления доступом: открытие двери подъезда, открытие калитки, открытие шлагбаума, если у пользователя есть соответствующие права. |
| FR-3 | Система должна получать от внешней платформы статусы устройств и результаты выполнения команд управления доступом. |
| FR-4 | Система должна получать от внешней платформы события доступа: успешный проход, отказ в доступе, событие распознавания лица, событие распознавания номера автомобиля, ошибки обработки. |
| FR-5 | Система должна обеспечивать проверку прав пользователя на выполнение действия в привязке к конкретному объекту: жилому комплексу, дому, подъезду, квартире, точке доступа, парковке. |
| FR-6 | Система должна поддерживать управление разрешёнными автомобилями пользователя для сценария интеллектуального шлагбаума. |
| FR-7 | Система должна поддерживать управление гостевыми и временными доступами, если это предусмотрено бизнес-процессом. |
| FR-8 | Система должна использовать внутренний интеграционный слой PropDevelopment как единую точку обмена данными с внешней платформой партнёра. |
| FR-9 | Система должна обеспечивать синхронизацию данных, необходимых для доступа: идентификатор пользователя, идентификатор объекта, список разрешённых точек доступа, разрешённые автомобили, статусы доступа. |
| FR-10 | Система должна обеспечивать отображение пользователю в мобильном приложении актуального состояния сервисов умного доступа и истории связанных событий в пределах разрешённых ему данных. |

## Нефункциональные требования (NFR)

| ID | Требование |
|---|---|
| NFR-1 | Все внешние интеграции должны выполняться **только через внутренний интеграционный шлюз / API Gateway** PropDevelopment. Прямой доступ мобильного приложения или внутренних БД к платформе партнёра должен быть запрещён. |
| NFR-2 | Все взаимодействия между системами предприятия и внешней платформой должны выполняться по защищённым каналам связи с использованием **TLS 1.2+**. |
| NFR-3 | Для сервис-сервис взаимодействия между PropDevelopment и внешней платформой должна использоваться **взаимная аутентификация по mTLS**. |
| NFR-4 | Для аутентификации и авторизации пользовательского доступа в мобильном приложении должен использоваться **OpenID Connect (OIDC)** поверх существующего сервиса аутентификации компании. |
| NFR-5 | Для авторизации взаимодействия между внутренними сервисами PropDevelopment и внешней платформой должен использоваться **OAuth 2.0 Client Credentials Flow**. |
| NFR-6 | Все access token, используемые при интеграции, должны иметь ограниченный срок жизни, передаваться только по защищённому каналу и содержать минимально необходимый набор claims и scopes. |
| NFR-7 | Авторизация должна строиться по принципу **минимальных привилегий (Least Privilege)**: внешняя платформа и внутренние сервисы получают только те права, которые необходимы для выполнения конкретной операции. |
| NFR-8 | В интеграции должна быть реализована **tenant isolation**: внешний партнёр, пользователь или оператор одной управляющей компании не должен иметь возможность видеть или изменять данные другой компании, другого жилого комплекса, другого дома или другого собственника. |
| NFR-9 | Должна использоваться комбинация **RBAC и ABAC**: роли пользователей и сервисов должны дополняться проверкой контекста доступа, включая объект недвижимости, устройство, тип операции, время и иные атрибуты. |
| NFR-10 | Внешней платформе должны передаваться только **минимально необходимые данные**. Передача избыточных персональных данных, не требуемых для работы сервиса, должна быть запрещена. |
| NFR-11 | Обработка биометрических данных должна быть выделена в отдельный защищённый контур. Использование биометрии должно выполняться только при наличии законного основания и соответствующих согласий, если они требуются. |
| NFR-12 | Все запросы и ответы внешней интеграции должны проходить **валидацию контрактов API**, включая проверку структуры, типов данных, обязательных атрибутов и допустимых значений. |
| NFR-13 | Для защиты от повторной отправки запросов и дублирования операций должны использоваться **idempotency key**, request ID, timestamp и механизмы replay protection. |
| NFR-14 | Для критичных операций должны использоваться механизмы контроля целостности данных: подпись сообщений, контроль версий записей, журналирование изменений, проверка корректности состояния. |
| NFR-15 | Интеграция должна обеспечивать **аудит и трассируемость** всех критичных действий: аутентификация, авторизация, выдача и отзыв прав доступа, открытие двери, открытие шлагбаума, ошибки интеграции, административные действия. |
| NFR-16 | Журналы безопасности и интеграционные события должны централизованно передаваться в систему аудита и мониторинга безопасности. |
| NFR-17 | Логи должны храниться с защитой от несанкционированного изменения и удаления, а чувствительные данные в логах должны маскироваться. |
| NFR-18 | Внешняя интеграция должна поддерживать мониторинг технического состояния: доступность API партнёра, ошибки вызовов, тайм-ауты, рост числа отказов, аномальные события доступа. |
| NFR-19 | Взаимодействие должно быть устойчивым к временным сбоям внешней платформы: должны поддерживаться повторные попытки, обработка тайм-аутов, безопасная деградация функций и фиксация ошибок. |
| NFR-20 | Доступ сотрудников PropDevelopment к настройкам интеграции и данным умного доступа должен разграничиваться по ролям и фиксироваться в журнале аудита. |
| NFR-21 | Все изменения прав доступа, привязок автомобилей, устройств и гостевых пропусков должны быть версионированы и доступны для последующей проверки в рамках аудита безопасности. |
| NFR-22 | Передача данных во внешнюю платформу, а также получение событий от неё, должны выполняться только через утверждённые и документированные API-контракты. |
| NFR-23 | Интеграция должна соответствовать требованиям законодательства РФ в части обработки персональных данных и, при применимости, биометрических персональных данных. |
| NFR-24 | Архитектура интеграции должна исключать прямой доступ внешнего партнёра к внутренним БД PropDevelopment, CRM, DWH и иным внутренним системам вне утверждённого интеграционного контура. |

## Протоколы аутентификации и авторизации

| Категория | Решение |
|---|---|
| Аутентификация пользователя | **OpenID Connect (OIDC)** |
| Авторизация доступа пользователя к API | **OAuth 2.0 access token** |
| Сервисная аутентификация между PropDevelopment и партнёром | **mTLS** |
| Сервисная авторизация между PropDevelopment и партнёром | **OAuth 2.0 Client Credentials** |
| Модель разграничения доступа | **RBAC + ABAC** |
| Защита транспортного уровня | **TLS 1.2+** |

## Организация взаимодействия между системами PropDevelopment и внешней платформой

| Этап | Описание взаимодействия |
|---|---|
| 1 | Собственник проходит аутентификацию в мобильном приложении PropDevelopment через внутренний сервис аутентификации по OIDC. |
| 2 | Мобильное приложение получает токен доступа и обращается только к внутренним API PropDevelopment. |
| 3 | Запрос на управление домофоном или шлагбаумом поступает во внутренний интеграционный шлюз PropDevelopment. |
| 4 | Интеграционный шлюз проверяет токен, права доступа, tenant isolation и корректность запроса. |
| 5 | Внутренний сервис бизнес-логики определяет, имеет ли пользователь право выполнить действие для конкретного объекта и устройства. |
| 6 | После успешной проверки внутренний шлюз отправляет во внешнюю платформу партнёра минимально необходимый запрос по защищённому API с использованием mTLS и OAuth 2.0. |
| 7 | Платформа партнёра управляет устройствами на объекте и возвращает результат выполнения команды или статус устройства. |
| 8 | События доступа, результаты распознавания и ошибки внешняя платформа передаёт обратно во внутренний интеграционный шлюз PropDevelopment через защищённый webhook/API. |
| 9 | Внутренние сервисы сохраняют результат, обновляют состояние и передают события в журнал аудита и мониторинга безопасности. |
| 10 | Пользователь видит результат операции и доступные ему статусы в мобильном приложении PropDevelopment. |
